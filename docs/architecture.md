# Архитектура Telegram-бота против прокрастинации

Oct 23, 2026 · @uy

## Обзор

Бот — один модульный монолит на Python: Telegram-слой принимает сообщения, доменные сервисы решают, что можно делать, база SQLite хранит всё состояние, а ИИ подключается через отдельный шлюз, который умеет работать с любым количеством провайдеров и ключей. Документ описывает, как это устроено, на основе ТЗ v0.9; кода здесь нет.

Главное отличие от ТЗ: вместо «OpenAI SDK через адаптер» вводится **ИИ-шлюз (LLM Gateway)**. Он прячет за единым интерфейсом OpenAI, Anthropic, Google Gemini, OpenRouter, локальные модели и любые OpenAI-совместимые API. Какую модель звать для какой задачи, решает конфигурация, а не код.

**Принципы, на которых держится архитектура:**

1. **Ядро работает без ИИ.** Задачи, таймеры, напоминания и кнопки не зависят от доступности моделей (ТЗ, этап A и сценарий G).
2. **ИИ только предлагает.** Модель возвращает структуру «предлагаемое действие», а код проверяет права по матрице FR-15 и либо применяет, либо просит подтверждение.
3. **База — единственный источник истины.** Таймеры, напоминания, ожидающие подтверждения живут в таблицах, а не в памяти процесса.
4. **Идемпотентность везде.** Каждый входящий update, нажатие кнопки, исходящее сообщение и запись в календарь имеет ключ операции.
5. **Провайдер ИИ — заменяемая деталь.** Ни один доменный сервис не знает, какая модель ему ответила.
6. **Открытые вопросы остаются открытыми.** Всё, что ТЗ не решило (раздел 10), вынесено в конфигурацию с пометкой «не утверждено», без выдуманных значений.

## Общая схема

&#91;embedded content: общая схема · 3 слоя, ИИ-шлюз и внешние сервисы\]

Сверху вниз: сообщение из Telegram проходит входной слой, доменные сервисы читают и пишут базу и при необходимости зовут ИИ-шлюз. Писать первым бот может только через привратник, а в календарь — только после явного подтверждения.

## Компоненты

Приложение делится на пять слоёв; зависимости идут только сверху вниз. Telegram-слой и будущий Mini App вызывают одни и те же сервисы, поэтому вторая система не появится (FR-16).

### 1. Входной слой

| Компонент | Что делает |
| --- | --- |
| Telegram Poller (aiogram 3, long polling) | Единственный экземпляр. Защищён файловой блокировкой и записью в `job_leases`, чтобы второй poller не запустился |
| Auth-middleware | Пропускает только разрешённый Telegram ID; чужим — нейтральный отказ без данных |
| Dedup-middleware | Пишет `update_id` в `processed_updates` в той же транзакции, что и результат обработки; повтор игнорируется |
| Router / обработчики | Команды, кнопки (callback), текст, голос. Тонкие: только разбор ввода и вызов сервиса |
| Conversation State | Текущий диалог и ожидание ответа в `conversation_states` (FSM aiogram с хранилищем в SQLite) |
| Voice Pipeline | Скачивает файл → распознаёт речь через ИИ-шлюз (задача `transcribe`) → передаёт текст в обычный конвейер. Ответ всегда текстовый |

### 2. Доменные сервисы

| Сервис | Отвечает за |
| --- | --- |
| TaskService | Цель → проект → этап → задача → подзадача, статусы, переносы, журнал `task_events` |
| GoalService | Долгосрочные цели, дорожные карты, прогресс (FR-10) |
| PlanningService | Утренний план, версии плана, перепланирование, калибровка оценок длительности |
| HabitService | Привычки, повторения, устойчивость без «обнуления» за пропуск |
| WorkSessionService | Таймер, Помодоро, короткий старт; источник и точность времени; записи задним числом |
| ReminderService | Планирует напоминания и решает, можно ли слать сейчас (см. «Привратник» ниже) |
| ProcrastinationAnalysisService + InterventionService | Быстрый вопрос → углублённый диалог; выбор способа помощи и запись его исхода |
| MemoryService | Факты и гипотезы с происхождением, сводки, каскадное удаление |
| CalendarService | Чтение занятости, кэш, создание события только по одобренному `pending_approval` |
| ApprovalService | Матрица разрешений FR-15, очередь предложений, просмотр массовых правок |
| AnalyticsService | Шесть направлений FR-11, вечерний и недельный отчёты |

### 3. Политика и безопасность действий

Все изменения, которые предложил ИИ, проходят через **Action Executor**. Модель возвращает список типизированных действий (`create_task`, `reorder_tasks`, `create_subtasks`, `reschedule_task`, `create_calendar_event` и т.д.). Исполнитель для каждого спрашивает ApprovalService:

- **разрешено без подтверждения** (порядок задач, напоминания, подзадачи, способ помощи) → проверить ограничения и применить в транзакции;
- **нужно согласие** → записать в `pending_approvals` и показать карточку с кнопками «Принять / Изменить / Отклонить»;
- **запрещено** (изменить или удалить чужую встречу) → отбросить и записать в аудит.

Свободный текст модели никогда не исполняется: он только показывается пользователю. Подтверждение — кнопка или однозначное «да» на конкретную карточку; молчание согласием не считается, у карточки есть срок жизни.

### 4. Фоновый планировщик и привратник

**Scheduler Loop** — один асинхронный цикл в том же процессе. Раз в N секунд (настройка) он читает из `reminder_schedule` записи с наступившим временем, берёт на каждую аренду в `job_leases` и отдаёт привратнику. Оттуда же запускаются утренний план, вечерний разбор, недельный отчёт, пересчёт сводок памяти и бэкап.

**Привратник (Outbound Gate)** — единственная точка, через которую бот пишет первым. Перед отправкой он проверяет по порядку:

1. категория сообщения — одна из шести разрешённых (FR-07);
2. не часы тишины, не ручная пауза, не занятость по календарю;
3. нет активной рабочей сессии (кроме сигналов таймера);
4. **скользящий лимит 4 напоминания за 60 минут** — считается по `outbound_messages` внутри той же транзакции `BEGIN IMMEDIATE`, поэтому два параллельных задания не обойдут лимит;
5. ключ дедупликации сообщения ещё не использован.

Если отправить нельзя, напоминание не копится, а **переоценивается**: ещё актуально → перенести на ближайшее допустимое время; устарело → включить в одну краткую сводку. Как считать утренние/вечерние отчёты относительно лимита — открытый вопрос № 3, поэтому в конфигурации для каждой категории есть флаг `counts_toward_limit` без значения по умолчанию.

**Надёжная отправка:** сначала запись `outbound_messages` со статусом `sending` и ключом операции, потом вызов Telegram, потом `sent` + `message_id`. При рестарте записи в `sending` не переотправляются вслепую: старые помечаются «возможно доставлено», свежие переоцениваются.

### 5. Хранилище

SQLite в режиме WAL на постоянном томе, SQLAlchemy 2 + Alembic. Доступ через репозитории и Unit of Work: одно действие пользователя = одна транзакция, ответ «готово» — только после commit. Время хранится в UTC, плюс IANA-пояс в профиле; локальные правила (часы тишины, «в 9:00») хранятся как локальное время + пояс и пересчитываются на каждую дату, чтобы переход на летнее время ничего не сдвигал. Секреты (ключи ИИ, OAuth-токены) в БД лежат только зашифрованными.

## ИИ-шлюз: несколько провайдеров и ключей

Доменный сервис никогда не выбирает модель сам. Он вызывает шлюз с именем задачи и ожидаемой схемой ответа, например `run(task="plan_day", schema=DayPlanProposal)`, и получает либо проверенный объект, либо явный отказ `AIUnavailable`. Всё остальное (какой провайдер, какой ключ, что делать при ошибке, сколько это стоило) решается внутри шлюза по конфигурации.

&#91;embedded content: путь одного вызова через ИИ-шлюз · запасные варианты\]

Ошибка API или невалидный ответ возвращают запрос к маршрутизатору за следующим кандидатом; если кандидаты кончились, сервис получает `AIUnavailable` и работает без ИИ.

### Из чего состоит шлюз

| Часть | Назначение |
| --- | --- |
| Реестр ИИ-задач | Для каждой задачи: шаблон промпта, Pydantic-схема ответа, уровень модели, бюджет контекста, требуемые возможности |
| Context Builder | Собирает контекст из профиля, сводок памяти, задач и календаря в пределах бюджета токенов; помечает пользовательский и внешний текст как данные, а не инструкции |
| Маршрутизатор | Превращает «задача + ситуация» в упорядоченный список кандидатов «провайдер + модель + ключ» с учётом эскалации, здоровья ключей и бюджета |
| Реестр ключей | Хранит зашифрованные ключи, их статус и лимиты; ведёт circuit breaker на каждый ключ |
| Адаптеры провайдеров | Переводят единый запрос в API конкретного провайдера и обратно, нормализуют ошибки и счётчики токенов |
| Валидатор и ремонт | Проверяет ответ Pydantic-схемой на нашей стороне всегда, даже если провайдер обещал строгий JSON |
| Учёт и аудит | Пишет в `ai_calls` токены, стоимость, задержку, маршрут, попытки и итог; следит за бюджетом |

### Адаптеры провайдеров

У всех адаптеров один интерфейс: `complete(request) → response` для текста и `transcribe(audio) → text` для голоса. Каждый адаптер объявляет свои возможности, и маршрутизатор не отправит задачу туда, где нужной возможности нет.

| Адаптер | Покрывает |
| --- | --- |
| `openai` | OpenAI |
| `openai_compatible` | Любой API в формате OpenAI по `base_url`: OpenRouter, DeepSeek, Groq, Mistral, локальные Ollama / LM Studio / vLLM |
| `anthropic` | Claude (Anthropic API) |
| `gemini` | Google Gemini |
| `fake` | Только для тестов: отдаёт записанные ответы, ошибки и невалидный JSON |

Дескриптор возможностей модели (задаётся в конфигурации, а не угадывается): `structured_output` (native\_schema / tool\_call / json\_mode / none), `max_context_tokens`, `max_output_tokens`, `audio_input`, `vision`, цены за входные и выходные токены или минуту аудио.

**Реализация адаптеров — два варианта.** (а) Тонкие собственные адаптеры на официальных SDK: полный контроль над структурированным выводом и ошибками, но четыре адаптера нужно поддерживать. (б) Универсальная библиотека вроде LiteLLM под тем же интерфейсом: сотни провайдеров сразу, но лишняя зависимость и меньше контроля. Рекомендация: вариант (а), потому что `openai_compatible` уже покрывает большинство сервисов, а внешний интерфейс шлюза не меняется при любом выборе. Актуальные возможности каждого API проверяются при реализации.

### Реестр ИИ-задач и уровни моделей

Уровень (tier) — абстракция между задачей и конкретной моделью. В коде задача ссылается на уровень, а какие модели и ключи стоят за уровнем, решает конфиг. Конкретные модели не выбраны (открытый вопрос № 7).

| ИИ-задача | Где нужна | Уровень | Возможности |
| --- | --- | --- | --- |
| `transcribe` | Голосовые сообщения | stt | audio\_input |
| `classify_intent` | Понять, что хочет пользователь, если не сработали команды и кнопки | fast | structured |
| `extract_tasks` | Черновики задач из текста (сценарий A) | standard | structured |
| `chat_reply` | Обычный ответ в диалоге с учётом стиля FR-08 | standard | text |
| `estimate_and_decompose` | Оценка длительности, подзадачи, «очень маленький шаг» | standard | structured |
| `plan_day` / `replan` | Утренний план и пересмотр | strong | structured, длинный контекст |
| `procrastination_dialog` | Углублённый разбор повторных переносов | strong | structured |
| `daily_review` / `weekly_analysis` | Вечерний и недельный разбор, гипотезы | standard / strong | structured, длинный контекст |
| `memory_summarize` | Пересборка сводок памяти | fast / standard | structured |

Напоминания, таймеры, кнопки и команды ИИ не вызывают совсем (FR-14).

### Маршрутизация и эскалация

Конфиг шлюза — один YAML-файл (плюс переопределения из бота), версии которого записываются в аудит. Пример структуры (имена моделей — заглушки):

```yaml
models:
  provA-small:  {provider: openai_compatible, credential: openrouter-main, model: "<id>", structured_output: native_schema, price_in: "<цена>", price_out: "<цена>"}
  provB-large:  {provider: anthropic, credential: anthropic-main, model: "<id>", structured_output: tool_call}
  provC-large:  {provider: gemini, credential: gemini-main, model: "<id>", structured_output: native_schema}
  local-small:  {provider: openai_compatible, credential: ollama-local, model: "<id>", structured_output: json_mode}

tiers:
  fast:     [provA-small, local-small]
  standard: [provB-large, provA-small]
  strong:   [provB-large, provC-large]
  stt:      [<stt-модель>]

escalation:
  - when: validation_failed_twice      -> next_tier
  - when: task_postponed_times >= "<не утверждено>" -> strong

budget:
  monthly_hard_usd: "<не утверждено>"
  on_soft_limit: downgrade_one_tier
  on_hard_limit: no_ai_mode
```

Алгоритм выбора для одного вызова:

1. Взять уровень задачи и применить правила эскалации.
2. Оставить кандидатов, у которых есть нужные возможности и хватает контекста.
3. Убрать кандидатов с отключённым или «остывающим» после ошибок ключом (circuit breaker открыт).
4. Если достигнут мягкий лимит бюджета — понизить уровень; жёсткий — вернуть `AIUnavailable`.
5. Пробовать кандидатов по порядку до первого валидного ответа, не превышая общий лимит попыток и времени на вызов.

### Ключи: хранение и ротация

- Ключей может быть сколько угодно, в том числе несколько у одного провайдера. Каждая запись `ai_credentials`: метка, провайдер, `base_url`, зашифрованный ключ, последние 4 символа для показа, статус (active / cooling\_down / disabled), собственный лимит расходов.
- Ключи шифруются мастер-ключом (AES-GCM / Fernet) из переменной окружения; мастер-ключ не попадает в базу и бэкапы. В логах и `ai_calls` — только метка ключа.
- Добавить ключ можно двумя способами: через `.env` при деплое или командой в боте (например, «Настройки → ИИ → Ключи»). Во втором случае бот сразу удаляет сообщение с ключом из чата, делает пробный запрос и показывает, какие модели доступны.
- **Ротация:** при 429 или исчерпанной квоте ключ уходит в `cooling_down` на время из `Retry-After` (или по экспоненциальной задержке), и берётся следующий кандидат. При 401/403 ключ отключается, и бот один раз сообщает владельцу.

### Структурированные ответы на разных провайдерах

Провайдеры по-разному умеют возвращать JSON. Одна Pydantic-модель — источник истины; адаптер выбирает лучший доступный способ:

1. **native\_schema** — провайдер принимает JSON Schema и гарантирует форму ответа;
2. **tool\_call** — схема оформляется как единственный инструмент, который модель обязана вызвать;
3. **json\_mode** — «верни JSON» + схема в промпте;
4. **none** — такие модели допускаются только для текстовых задач (`chat_reply`).

После любого способа ответ проходит проверку Pydantic и бизнес-проверки (ссылки на существующие `task_id`, время в допустимом диапазоне). Невалидно → одна попытка «ремонта» у той же модели с текстом ошибок → следующий кандидат → `AIUnavailable`. На `AIUnavailable` сервис включает безопасный сценарий: шаблонный ответ, ручные кнопки, никаких изменений по догадке.

### Ошибки и запасные варианты

| Тип ошибки | Реакция шлюза |
| --- | --- |
| Таймаут, 5xx, сеть | Повтор с экспоненциальной задержкой (несколько попыток), затем следующий кандидат |
| 429 / квота | Ключ в cooling\_down, сразу следующий кандидат |
| 401 / 403 | Ключ disabled, одно уведомление владельцу, следующий кандидат |
| 400 (неверный запрос, контекст слишком длинный) | Без повтора на той же модели; следующий кандидат с большим контекстом или сокращённый контекст |
| Отказ модели отвечать | Следующий кандидат или безопасный сценарий |
| Невалидная структура | Ремонт → следующий кандидат → безопасный сценарий |

Если все кандидаты долго недоступны, бот переходит в режим «без ИИ» и один раз сообщает об этом; пробные запросы из фонового цикла возвращают его автоматически.

### Учёт стоимости

- Цены задаются в конфиге для каждой модели; токены берутся из ответа провайдера (если их нет — оценка с пометкой `estimated`). Стоимость каждой попытки, включая неудачные, пишется в `ai_calls`.
- Отчёт «Расходы ИИ» в настройках: за день/месяц, по провайдерам, ключам, моделям и типам задач.
- Предупреждение об аномальном росте (расход за день сильно выше среднего). Ресурсоёмкие функции (недельный анализ, пересборка памяти) выключаются флагом.
- Размер бюджета и пороги — открытый вопрос № 7; до решения лимиты не включены, идёт только учёт.

### Приватность при нескольких провайдерах

Личные данные уходят каждому провайдеру, который получил запрос. Поэтому у каждого ключа есть настройка `allowed_data`: например, разрешить провайдеру только текущее сообщение, без памяти и истории. Маршрутизатор учитывает это при выборе кандидата. Это предложение архитектуры, а не утверждённое требование; по умолчанию все ключи равноправны.

### Тестирование

Бизнес-правила тестируются на адаптере `fake`. Для каждого реального адаптера есть контрактные тесты на записанных ответах (нормализация ошибок, токенов, структурированного вывода) и необязательный «живой» прогон по команде. Набор «сложных случаев» из раздела 8 ТЗ прогоняется на каждой настроенной модели, чтобы сравнить провайдеров перед включением в маршрут.

## Модель данных

За основу взята логическая схема из раздела 5 ТЗ; ниже только то, что архитектура добавляет или уточняет. Таблицы сгруппированы по сервису-владельцу: пишет в таблицу только её сервис, остальные читают.

| Группа | Таблицы | Владелец | Что добавляет архитектура |
| --- | --- | --- | --- |
| Профиль | `owner_profile`, `settings` | — | Персонаж и стиль как набор независимых параметров (строгость, юмор, мат, длина) |
| Структура работы | `goals`, `projects`, `milestones`, `tasks`, `categories`, `contexts` | TaskService, GoalService | `tasks.parent_id` для подзадач; поле `importance` без зафиксированной шкалы (открытый вопрос № 4) |
| Журналы | `task_events`, `audit_log` | все сервисы | Только добавление, без изменения; у каждого события `actor` (user / system / ai) |
| Планы | `daily_plans`, `plan_items`, `plan_revisions` | PlanningService | Статусы версии: proposed → approved → revised → closed |
| Работа | `work_sessions`, `session_pauses` | WorkSessionService | `time_source` (exact / retro / approximate) и `confidence`; статус `unconfirmed` по умолчанию |
| Привычки | `habits`, `habit_occurrences` | HabitService | — |
| Уведомления | `reminder_schedule`, `outbound_messages` | ReminderService | `category`, `dedup_key`, `send_state` (planned / sending / sent / maybe\_sent / folded / cancelled) |
| Диалог | `conversation_messages`, `conversation_states` | входной слой | Срок хранения не задан (открытый вопрос № 8) |
| Память | `memory_items`, `memory_summaries`, `memory_sources` | MemoryService | См. ниже |
| Помощь | `behavior_observations`, `interventions`, `intervention_outcomes` | Analysis / Intervention | Исход связан с рабочей сессией, если она была |
| Календарь | `calendar_connections`, `calendar_event_cache`, `calendar_event_links` | CalendarService | Время последней синхронизации, чтобы показывать «данные могут быть неактуальны» |
| Подтверждения | `pending_approvals` | ApprovalService | Типизированный `action_payload`, `diff` для просмотра, `expires_at`, `resolution` |
| **ИИ (новое)** | `ai_credentials`, `ai_routing_config`, `ai_calls`, `ai_call_attempts`, `ai_budget_ledger` | AI Gateway | Ключи, версии конфига, вызовы и каждая попытка с ценой |
| Техническое | `processed_updates`, `job_leases`, `backup_manifest` | инфраструктура | — |

**Память с происхождением.** У каждой записи `memory_items` есть `kind` (fact / preference / pattern / hypothesis) и `origin` (user\_said / system\_measured / ai\_inferred / user\_confirmed / user\_refuted). `memory_sources` связывает запись с первичными сообщениями и событиями, а каждая сводка — со списком записей, из которых собрана. При удалении записи все сводки, где она участвовала, помечаются недействительными и собираются заново без неё; до пересборки Context Builder их не использует (критерий приёмки 20).

**Что лежит в `ai_calls`** (аудит ИИ по ТЗ, раздел 7): ИИ-задача, инициатор, уровень и причина эскалации, выбранные провайдер / модель / метка ключа, токены и цена, время, итог валидации, предложенные действия и что с ними стало (применено / ждёт подтверждения / отклонено). Полные тексты промптов и ответов хранятся отдельно и недолго, но срок — открытый вопрос № 8.

## Ключевые сценарии

Во всех сценариях одна форма: вход → (при необходимости) ИИ-шлюз возвращает предложение → Action Executor и ApprovalService решают, применить или спросить → транзакция → ответ. ИИ нигде не пишет в базу напрямую.

### A. Свободная постановка задач (текст или голос)

1. Poller получает update; Auth и Dedup пропускают его один раз.
2. Голос → `transcribe` через шлюз. Текст распознавания показывается пользователю вместе с ответом.
3. `extract_tasks` возвращает кандидатов: название, предполагаемый срок, связь с целью, список неопределённостей.
4. Создание самостоятельной задачи требует согласия → кандидаты ложатся в `pending_approvals`, бот показывает карточку.
5. Кнопка «Принять» → TaskService создаёт задачи в одной транзакции; повторное нажатие дублей не даёт.

Как именно показывать несколько кандидатов и что делать с неоднозначными фразами (принять все / по одной / сначала уточнить) — вопрос 36, он открыт. Архитектура поддерживает любой из вариантов, а до решения действует правило «только с подтверждением».

### B. Утреннее планирование

1. Scheduler в заданное пользователем время запускает PlanningService.
2. CalendarService отдаёт занятые интервалы (или кэш с пометкой устаревания).
3. **Код** считает свободные окна, обязательные сроки, историю точности оценок и резерв на перерывы.
4. `plan_day` получает это как данные и возвращает раскладку с объяснением приоритетов.
5. Код проверяет: ничего не стоит поверх встреч, сроки не нарушены, окна не забиты целиком. Нарушение → ремонт или детерминированный план без ИИ.
6. План сохраняется как версия `proposed`; после подтверждения — `approved`, и ReminderService строит напоминания по плану.

### C. Задержка начала

1. Время начала прошло, сессия не подтверждена → в `reminder_schedule` срабатывает запись категории «нет подтверждения начала».
2. Привратник проверяет тишину, паузу, календарь и лимит 4/60.
3. Короткий вопрос с кнопками причин — шаблон, ИИ не нужен.
4. Ответ «не понимаю, с чего начать» → `estimate_and_decompose` предлагает маленький шаг; подзадача создаётся без подтверждения (разрешено FR-15).
5. Интервенция и её исход записываются. При повторе или неясности — `procrastination_dialog` на сильном уровне. Порог перехода — открытый вопрос № 4.

### D–F. Рабочая сессия, отчёт, задний числом

- Старт сессии записывает в базу `started_at` и планирует только сигналы таймера; остальные напоминания на это время блокирует привратник.
- Завершение: простая задача закрывается кнопкой; важная — сверка с критерием готовности. Исходы: начал / продвинулся / завершил.
- «Я работал с двух до четырёх» → ИИ извлекает интервал, бот уточняет, сессия создаётся с `time_source = retro` и записью в журнале исправлений.

### G. Перезапуск после сбоя

1. Процесс стартует, берёт блокировку единственного экземпляра, применяет миграции.
2. Recovery-шаг: истёкшие аренды освобождаются, сообщения `sending` разбираются, пропущенные напоминания переоцениваются и сворачиваются в одну сводку.
3. Активные сессии восстанавливаются из базы; сигналы таймера пересчитываются от сохранённого `started_at`.
4. Только после этого стартуют Poller и Scheduler. Если ИИ недоступен, бот работает в режиме «без ИИ».

### H. Недельный разбор

AnalyticsService считает метрики кодом (выполнение, задержка старта с учётом качества источника времени, исходы интервенций, цели). `weekly_analysis` пишет только текст и гипотезы на основе готовых цифр, сам цифры не считает. Гипотезы сохраняются с `origin = ai_inferred`; если пользователь их опровергает, они получают `user_refuted` и выходят из контекста.

## Надёжность, безопасность, развёртывание

Бот разворачивается одним контейнером приложения через Docker Compose на небольшом Linux VPS; база и бэкапы лежат на постоянных томах. Внутри процесса три асинхронные задачи: Poller, Scheduler Loop и фоновая синхронизация календаря. Один процесс проще для SQLite и для лимита уведомлений; если позже понадобится отдельный воркер, аренды в `job_leases` уже защищают от двойной обработки.

| Требование ТЗ | Как обеспечено |
| --- | --- |
| Долговечность | Одна транзакция на действие, ответ пользователю — после commit |
| Дедупликация | `processed_updates` для входящих; ключи операций для кнопок, исходящих и событий календаря (в описание созданного события пишется метка для сверки) |
| Работа без ИИ | Шлюз возвращает `AIUnavailable`; у каждого сервиса есть шаблонная ветка |
| Повторы | Экспоненциальная задержка с лимитом попыток для Telegram, Calendar и ИИ; о существенных сбоях — одно сообщение, без спама |
| Бэкапы | SQLite Online Backup API → сжатие → шифрование → запись в `backup_manifest`; скрипт восстановления на чистом окружении в автотестах. Периодичность, срок хранения и копии вне сервера — открытые вопросы № 8 и 10 |
| Секреты | Telegram-токен и мастер-ключ — в окружении; ключи ИИ и OAuth-токены — в базе в зашифрованном виде; бэкапы не содержат ключей в открытом виде |
| Внедрение инструкций | Пользовательский текст, события календаря и память передаются модели как помеченные данные; любое действие всё равно проходит матрицу разрешений |
| Google Calendar | Минимальные scopes; в коде есть только методы чтения и `insert`; `update`/`delete` чужих событий в клиенте не реализуются вообще. Какие календари и scopes — открытый вопрос № 6 |
| Удаление данных | Каскад через `memory_sources` и сводки; экспорт в JSON; без обещаний стереть данные у внешних провайдеров ИИ |
| Время и DST | UTC в базе, IANA-пояс в профиле; часы `Clock` внедряются в сервисы, чтобы тесты фиксировали время |

**Наблюдаемость.** Структурные JSON-логи с `correlation_id` от update до ИИ-вызова и ответа, без ключей и полных текстов сообщений. Команда `/status` для владельца: версия, время работы, состояние каждого ключа ИИ, синхронизация календаря, последний бэкап, расходы за месяц. Внешнее оповещение о падении бота — открытый вопрос № 10; архитектура оставляет для него healthcheck-эндпоинт в контейнере.

**Этапы из ТЗ на архитектуре.** Этап A строит входной слой, хранилище, планировщик, привратник и ApprovalService — без ИИ. Этап B добавляет ИИ-шлюз сразу с двумя провайдерами и адаптером `fake`, чтобы многопровайдерность проверялась с первого дня. Этап C — CalendarService, привычки, цели, аналитика, управление памятью. Этап D — Mini App: тонкий HTTP API с проверкой Telegram `initData` поверх тех же сервисов и той же базы.

## Открытые вопросы

Архитектура не отвечает на вопросы из раздела 10 ТЗ, а оставляет для каждого место в конфигурации или настройках. Пока ответа нет, действует безопасное поведение из третьей колонки.

| № | Вопрос | Где отражается / что действует до ответа |
| --- | --- | --- |
| 1 (вопрос 36) | Неоднозначные фразы и несколько задач в одном сообщении | Сценарий A. Любая самостоятельная задача — только через `pending_approvals` |
| 2 | Часы сна, тишины, будни/выходные, время утреннего/вечернего/недельного обзора | `owner_profile`, заполняется на онбординге. Не задано → соответствующий инициативный отчёт не шлётся, бот спрашивает |
| 3 | Интервалы напоминаний, лимит серии, учёт сервисных сообщений в лимите 4/60 | Конфиг привратника, флаг `counts_toward_limit` по категориям. Лимит 4/60 для напоминаний действует всегда |
| 4 | Шкала важности, критерии «важной» задачи, переход к глубокому диалогу | Поле `tasks.importance` и правила эскалации в конфиге. До решения важность ставит пользователь |
| 5 | Настройки Помодоро, короткого старта, перерывов | Пользовательские настройки; при первом запуске режима бот спрашивает длительность |
| 6 | Какие календари Google читать, в какой создавать, OAuth-права | `calendar_connections`: список календарей для чтения и календарь для записи выбираются при подключении |
| 7 | Конкретные ИИ-провайдеры, модели, месячный бюджет | Конфиг шлюза (`models`, `tiers`, `budget`). Благодаря шлюзу этот выбор не блокирует разработку; до решения идёт учёт без лимитов |
| 8 | Сроки хранения сообщений, файлов, памяти, бэкапов, политика удаления и экспорта | Настройки retention; до решения ничего автоматически не удаляется, ручное удаление работает |
| 9 | Форма отчётов и дизайн Mini App | Шаблоны отчётов отделены от расчёта метрик; Mini App — этап D |
| 10 | Размещение VPS, копии вне сервера, оповещение о падении | Цель для бэкапа — настройка (локальный том или внешнее хранилище); healthcheck готов для внешнего мониторинга |
